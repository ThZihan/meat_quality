What a BLE store-and-forward link actually costs

Moving an ESP32 sensor node off WiFi and onto Bluetooth Low Energy, with the Raspberry Pi gateway — not the cloud — as the point of durability. The protocol was straightforward to specify. Making it hold on real hardware took five defects, two corrupted diagnostic channels, and a set of GATT behaviours that no specification predicts. This is the complete record.

How to read the evidence markers

Every claim in this report carries its provenance, because the distinction mattered repeatedly during the work: Measured observed on this hardware; Calculated derived from measured unit costs; By code path reasoned from the implementation, not exercised; Unresolved known behaviour without a root cause.

01

Notification delivery is robust. GATT writes are not.

The single most transferable result from the project, and the one that cost the most time to isolate.

Every obstacle in this section presented identically at the symptom level: “BLE is flaky, the link keeps dropping.” None of them was a radio problem. RSSI held between −31 and −33 dBm throughout, at 25 cm separation, with a negotiated ATT MTU of 247 bytes and payloads of 146–163 bytes — one notification per reading, no fragmentation. The link had enormous margin. It still would not stay up.

The causes were all in how the two stacks handled writes. Each row below is a controlled trial holding everything else fixed.

The contrast is stark. Under a per-reading acknowledgement regime this hardware managed one reading per connection before tearing down. With writes minimised, the same hardware held a single connection for the entire test window and streamed 50+ notifications — stored=51 duplicates=5, zero disconnects.

Five rules that follow

  1. Use response=True for every write. This is counter-intuitive: write-without-response is the lighter operation and the obvious choice for a high-rate acknowledgement channel. It is also the one that kills the link.
  2. Subscribe before writing anything. A write issued before StartNotify leaves BlueZ silently never delivering notifications. The peripheral transmits — confirmed on its serial console — and the central’s callback never fires. Nothing raises.
  3. Acknowledge cumulatively and rate-limit. One write per second clearing everything up to a sequence number, rather than one write per reading.
  4. Serialise all writes behind one lock. Two writes racing on a single connection drop it about two seconds later.
  5. Never write from inside a notification callback. It runs on BlueZ’s D-Bus dispatch path. The final implementation has the callback do nothing but queue.put_nowait(bytes(raw)), with a separate worker performing storage and acknowledgement.
Scope of this claim

These are observations on one widely-deployed stack pairing — BlueZ 5.82 with bleak 3.0.2 against NimBLE-Arduino 2.2.x. They may not generalise to Android, iOS or Windows centrals, or to Bluedroid on the peripheral side. Frame them as “observed on this Linux stack”, not as universal BLE behaviour. Testing whether they reproduce under Bluedroid is the fastest way to determine whether this is a NimBLE issue, a BlueZ issue, or an interaction between them.

02

The MTU your client reports is not the MTU you have

bleak reported client.mtu_size as 23 — the ATT default — while the peripheral’s own onMTUChange callback reported a negotiated 247, and BlueZ’s D-Bus characteristic properties independently showed MTU: 247.

The library emits UserWarning: Using default MTU value. Call _acquire_mtu()…. The value is unqueried, not negotiated down to 23. Considerable design effort went into fitting a reading into a 20-byte payload — scaled 16-bit integers, chunking schemes — against a constraint that did not exist.

Rule

Trust the peripheral’s negotiated value or BlueZ’s MTU property. Do not trust the client library’s default-valued attribute.

03

BlueZ caches the GATT database and never invalidates it

A host-side cache producing a data-integrity failure invisible to the application.

BlueZ stores a resolved copy of each peer’s attribute table under /var/lib/bluetooth/<adapter>/cache/<device>. Any firmware change that alters the characteristic layout invalidates that cache, and BlueZ does not detect the change.

Stale handle mappings produced a phantom acknowledgement. The peripheral logged:

[ACK] seq<=1004 confirmed — 1 cleared, 232 still queued

for a write the gateway had never issued. A queued reading was silently discarded. This is data loss caused entirely by host-side caching, with no application-visible cause.

Defensive mitigation, now in firmware

The ACK handler rejects any write that is not exactly four bytes, and rejects any sequence number above the highest actually transmitted (lastSentSeq). A stale or spurious write can no longer discard queued data.

Operational mitigation, after any GATT profile change

bluetoothctl remove <NODE_MAC>
sudo rm -rf /var/lib/bluetooth/<ADAPTER_MAC>/cache/<NODE_MAC>
sudo systemctl restart bluetooth

NimBLE encodes BLE_HS_ERR_HCI_BASE = 0x200 plus the HCI error:

05

What remains unexplained

Under sustained load the link still re-establishes roughly every 30 seconds. Unresolved

This is not a data-loss path. Nothing leaves the node’s queue until acknowledged, and duplicates collapse on the UNIQUE index — the reconnection overlap is visible in the data as duplicates=5 against stored=51, absorbed exactly as designed. Measured throughput comfortably exceeds the production rate: 79 readings ingested in a 180-second window while the node generated 60, so backlogs drain rather than grow.

But it is unexplained, and that is worth disclosing rather than papering over. Candidate hypotheses not yet eliminated: connection-parameter negotiation; WiFi/BLE coexistence on the Pi 5’s shared 2.4 GHz front-end, since WiFi is active for the uplink; NimBLE host-task starvation during ADC bursts (32 samples × 3 channels ≈ 26 ms per cycle); or BlueZ state degradation across many reconnect cycles. A btmon HCI capture correlated against the node’s serial log across a single disconnect would settle it.

06

Why the WiFi architecture had to go

The failure was architectural, not implementational — which is the more useful finding.

In the original design the ESP32 held WiFi credentials in EEPROM, exposed a SoftAP captive portal for provisioning, obtained wall-clock time over NTP, and POSTed JSON directly to the cloud over TLS. The Raspberry Pi polled the server’s /history endpoint every five seconds and mirrored new rows into local SQLite for the dashboard.

The cloud server therefore sat upstream of the Pi. The Pi could not obtain data the server had not received — even though the node and the gateway were on the same bench, 25 cm apart. A server or internet outage meant no data reached the Pi at all.

The buffer was nowhere near adequate

The node’s offline queue was MAX_QUEUE = 20 entries in RAM, drained three per cycle. At a 3-second sampling interval that is sixty seconds of protection, and it was volatile — a reboot lost it. Beyond 60 s the firmware shifted the ring and dropped the oldest entry, incrementing a queueDropCount that nothing acted on.

Secondary couplings, all removed by the change

  • Timestamps depended on NTP, which depended on WiFi. With no WiFi the firmware emitted the literal string 1970-01-01T00:00:00Z. Since deduplication and bookmarking keyed on timestamps, this was actively corrupting.
  • Identity was assigned by the server. Deduplication used a server-issued source_id, so the Pi could only identify a reading after the server had accepted it.
  • Server ids could reset on a database restore, which the client defended against with a 24-hour lookback window — complexity caused purely by the server owning identity.
Generalisable

“Device → cloud → dashboard” is the reference topology in most IoT material, and it rarely asks what holds the data when the middle link is down. Where the first durable store sits is the architectural decision; everything else is detail.

07

What removing WiFi entirely bought and cost

The node has no WiFi, no HTTP, no TLS and no NTP. BLE is its only link, and the gateway 25 cm away is its only consumer.

  • No NTP. Solved with two independent mechanisms (§10) rather than by adding an RTC — which would have been the obvious hardware answer but adds a part, a battery, and a failure mode.
  • Self-assigned identity. The node issues its own monotonic sequence numbers, so a reading has an identity from the moment of capture rather than from the moment a server accepts it.
  • No provisioning portal. Roughly 460 lines of SoftAP, DNS and captive-portal code deleted, along with the EEPROM credential store.
  • The wifi_rssi field became meaningless. It now carries BLE link RSSI, which keeps the dashboard’s signal display working, with sensor_status.link = "ble" recorded per row so the provenance is explicit in the data rather than implied.

Dropping the entire WiFi/TLS/portal stack and adding NimBLE was close to footprint-neutral in flash while freeing the RAM budget that the reading queue consumes. NimBLE rather than the bundled Bluedroid stack was deliberate: Bluedroid is substantially larger in both flash and RAM, and RAM headroom is precisely what the queue needs.

09

The delivery guarantee, stated precisely

At-least-once on the wire, exactly-once in the database. The ordering is the entire guarantee.

Duplicates from a retransmission collapse on the UNIQUE index over sensor_readings.source_id, written with INSERT OR IGNORE. The source_id is "<device_id>:<seq>", stable across retransmits by construction — which is only possible because the node, not the server, owns identity.

The gateway withholds the acknowledgement on

  • an undecodable payload,
  • a missing sequence number,
  • a SQLite insert failure — including disk-full,
  • failure to enqueue the upload job.

Each leaves the reading in the node’s queue for retransmission. The last of these was a defect for most of the project’s life (§16).

Sentinel collision — a bug worth reporting on its own

Sequence numbers must start at 1, never 0, because 0 is also the initial value of lastAckedSeq, and ackUpTo() opens with if (seq <= lastAckedSeq) return;. A reading numbered 0 can therefore never be acknowledged. It pins the head of the queue and blocks every reading behind it, permanently.

This is only reachable on freshly-erased NVS — that is, on every new deployment. A device that has been running a while never exhibits it; a factory-fresh unit exhibits it every time. restoreQueue() now also discards any seq-0 entry it finds, because the queue survives reflashes.

10

Correct timestamps on a node with no clock

No RTC, no NTP. Two mechanisms, neither of which gates sampling or transmission.

Mechanism A — pushed clock (ep). The gateway writes epoch milliseconds to the TIME characteristic. The node stores an offset against millis() rather than an absolute time, so the derived clock cannot drift away from the monotonic ordering of readings. On receipt it also back-fills ep for readings already queued from the current boot, guarded by a boot id so that readings carried across a reboot are never given timestamps derived from a previous boot’s uptime.

Mechanism B — age since capture (ag). Every transmission carries the elapsed milliseconds between capture and that transmission, from the monotonic uptime counter. The gateway computes timestamp = pi_now − ag. It is recomputed on every retransmission, so it stays correct no matter how long a reading sat in the queue.

All three paths are exercised in real data, and the provenance of every timestamp is recorded in the row itself rather than assumed — which is worth something in a methods section.

Validation. A synthetic reading injected with ag = 30000 was stored exactly 30 seconds before its arrival time: arrival 09:45:57, stored 09:45:27. Measured Mechanism B is therefore accurate to the gateway’s own clock accuracy plus transmission latency — tens of milliseconds, far below the 3-second sampling interval.

The useful part

The pushed clock turned out to be unnecessary, and is now disabled by default. Age-based reconstruction is sufficient and strictly more robust, because it has no dependence on a successful GATT write — and GATT writes are the fragile half of this link (§01). A node with no RTC, no NTP and no clock at all still produces correctly timestamped data, as long as the gateway knows the time. That is a cheap, generalisable technique for cost- and power-constrained sensor nodes.

11

Spending the flash budget deliberately

Checkpointing the queue on every reading would be one write per 3 s — 28,800 writes per day. NVS wear-levels across its partition, but the underlying flash is rated on the order of 105 erase cycles per sector; at that rate a 20 KiB partition is being cycled hard enough to matter within months.

  • The queue lives in RAM. NVS is a crash-safety checkpoint, not the store.
  • Checkpointing begins only once the backlog reaches 20 readings — about a minute, i.e. evidence the gateway is actually gone — rate-limited to one write per minute, plus one immediate checkpoint on unexpected disconnect.
  • During normal operation the firmware performs zero flash writes.
  • Sequence numbers come from pre-reserved blocks of 1,000, costing one NVS write per ≈50 minutes rather than one per reading.
Reading the data later

A reboot burns the remainder of the current sequence block, so source_id values have gaps across reboots. This is harmless — the invariant required is uniqueness and monotonicity, not contiguity — but gaps look exactly like data loss to an analyst. Anyone working with the exported data needs to know this.

Thermal confound — affects any future spoilage study

Measured ambient temperature across the dataset ranged 33.8–39.1 °C. This is not refrigerated storage: it is open-bench ambient in a warm climate plus self-heating from the MQ heater array, which runs continuously at roughly 150 mW per element, physically adjacent to the BME280.

The temperature channel is currently measuring the enclosure, not the sample. For a spoilage study the BME280 must be thermally separated from the heaters. This is a hardware fix, not a software one, and it should be stated in any methods section.

14

Gas sensing circuit and its systematic error

The MQ modules output 0–5 V on AOUT; the ESP32 ADC accepts 0–3.3 V. A resistive divider scales it: Rupper 68 kΩ, Rlower 100 kΩ, ratio 1.68, with a 100 nF capacitor stabilising the node.

The divider is not electrically free. It loads the module’s own load resistor, and the firmware accounts for this with an effective load resistance — a detail commonly omitted in MQ-sensor work:

R_L(module)    = 10 kΩ
R_divider      = 68k + 100k = 168 kΩ
R_L(effective) = (10k × 168k) / (10k + 168k) = 9.438 kΩ

Using the nominal 10 kΩ instead introduces a 5.95 % systematic error in RS, which propagates through the power law with exponent 1/b to give 2.1–2.4 % in ppm depending on the gas. Calculated Small, but a reproducible bias rather than noise.

ADC conditioning

The 68k/100k divider presents a high source impedance to the ESP32 SAR ADC, known for mux and sample-and-hold artefacts. Mitigation: one throwaway conversion after channel switch to discard sample-and-hold residue from the previously selected channel, 500 µs settle, then 32 averaged conversions at 250 µs spacing, 12-bit resolution, 11 dB attenuation.

Conversion

V_node = (adc / 4095) × 3.3 × 1.68
RS     = ((5.0 − V_node) / V_node) × R_L(effective)
ppm    = ((RS / R0) / a) ^ (1 / b)

The weakest link in the measurement chain

R₀ is per-unit and drifts with sensor age and humidity. It was established once, in ambient air, with no humidity or temperature compensation — while measured RH spanned 53.9–79.5 % in this dataset alone, and MQ-series response is strongly humidity-dependent.

Worse for interpretation: these sensors are cross-sensitive. MQ-135 responds to NH₃, benzene, alcohol and smoke; MQ-136 responds to NH₃ and CO as well as H₂S. The firmware itself computes multiple candidate gases from the same MQ-135 and MQ-136 elements using different (a, b) pairs. Any claim that a channel measures a specific gas needs a reference instrument or a controlled gas exposure to defend.

Two threshold sets that disagree

A real inconsistency in the codebase, documented rather than quietly reconciled.

Edge — firmware, five labels, emitted per reading

Integration constraint found only in production

The cloud API rejects any quality label outside {EXCELLENT, GOOD, MODERATE, POOR, CRITICAL} with HTTP 400. An earlier firmware emitted FAIR and SPOILED and was silently failing to upload — a good example of a contract that no amount of local testing would have surfaced.

16

Nine durability defects, classified

Every one was invisible in code review and appeared only on hardware — or only under adversarial reasoning.

  1. 01 Sequence-number sentinel collision Reading 0 could never be acknowledged, pinning the queue head permanently. Class  A sentinel colliding with a legitimate value in the same domain. Reachable only on a factory-fresh device.
  2. 02 Silent NVS overflow A 31,680-byte checkpoint written to a 20,480-byte partition. putBytes returned 0, unchecked, while the recorded length still promised the data. Class  Unchecked return on a resource whose limit is defined outside the source file.
  3. 03 GATT write instability Per-reading acknowledgement drew ATT 0x0E and killed the link. Class  A protocol-level assumption — writes are cheap and safe — invalidated by a specific stack pairing.
  4. 04 Flash write inside a radio callback NVS writes disable the flash cache for tens of milliseconds, stalling the NimBLE host task. Class  Blocking operation in a latency-sensitive callback context.
  5. 05 ACK did not clear the in-flight marker After an acknowledgement cleared the queue head, the new head was judged in-flight against the previous send’s timestamp and waited the full 4 s timeout. A backlog drained at one reading per four seconds instead of ~16 per second. Class  Stale state after a state transition. Presented as poor throughput, not as a bug.
  6. 06 pending_sync never created by the schema initialiser It existed in the live database only as a leftover from an older schema. On a fresh install, readings would be stored locally and never uploaded. Class  Schema drift between a long-lived deployment and a clean install. The deployed system worked; a new one would not.
  7. 07 Transient upload failures parked rows permanently A network error counted against a 20-attempt limit; after ~5 minutes of downtime rows were marked failed, and the fetch query only ever selected pending. Nothing retried a parked row. Class  Conflating “retryable” with “failed”, plus a terminal state with no exit.
  8. 08 Enqueue failure swallowed and returned 0 A reading could land in sensor_readings, fail to be queued for upload, and still be acknowledged — so the node discarded its only other copy of a reading the server would never see. Class  Error suppression at a durability boundary.
  9. 09 Storage guard would not delete un-uploaded images A long uplink outage would fill the card, stall SQLite, stop acknowledgements, and overflow the node buffer — losing gas readings in order to preserve photographs. Class  A local invariant (“never delete unsent data”) producing a globally worse outcome.
The methodological point

Defects 06 through 09 were found by working through “what happens if X fails” as an explicit exercise, not by testing. That is itself a finding: the durability bugs were not reachable by normal testing, only by adversarial reasoning about the failure envelope. A test suite exercising the happy path at any coverage level would have passed all four.

17

When the instrument lies

The largest single time cost in the project was not design or implementation — it was a compromised diagnostic channel.

ModemManager versus the ESP32

ModemManager probes newly-appearing serial devices with AT commands and toggles DTR/RTS. On an ESP32 that asserts the auto-reset circuit. Symptoms observed:

  • Apparently impossible serial data rates — 38–62 KB/s measured on a 115200 baud line whose ceiling is 11.5 KB/s.
  • Truncated and interleaved log lines.
  • Boot banners never appearing.
  • Resets that made a healthy device look like it was crash-looping.

Every attempt to observe the firmware produced misleading evidence. Fix, now shipped as a udev rule:

ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", ENV{ID_MM_DEVICE_IGNORE}="1"
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", ENV{ID_MM_PORT_IGNORE}="1"

Kernel TTY buffering compounds it

An unread serial port accumulates a large kernel buffer. Opening it later and reading immediately returns stale backlog, which looks like a live flood. Any diagnostic reader must drain to quiescence before treating what it sees as current. Several apparently-contradictory observations during debugging were this artefact and nothing else.

Bluetooth ships soft-blocked

rfkill had Bluetooth soft-blocked at boot; hci0 showed DOWN despite bluetooth.service being active. Required once, and persisted thereafter by systemd-rfkill:

sudo rfkill unblock bluetooth
sudo sed -i 's/^#AutoEnable=true/AutoEnable=true/' /etc/bluetooth/main.conf

The NVS partition silently bounds the queue

The stock table allocates nvs 20,480 bytes. The originally-designed 720-reading checkpoint is 31,680 bytes — larger than the partition. Preferences::putBytes() failed, returned 0, and the code did not check it, while q_len was still written. The recorded length promised data the blob did not contain; restoreQueue() found the mismatch and discarded everything. Eventually the node wedged completely, with no serial output at all.

The attempted fix — a custom partition table with 64 KiB NVS, no OTA slots and a 3 MiB app — made it worse: the application reset before producing any output, rst:0x3 (SW_RESET) in a tight loop at ≈36 resets per second. It was not pursued. The supported configuration is the stock table with a bounded 128-reading checkpoint, the return value of putBytes checked, and q_len zeroed on failure so a partial write can never masquerade as a good one.

Transferable

On ESP32 the persistent-storage budget is a partition-table constant most projects never revisit, and exceeding it fails silently rather than exceptionally. More generally: when a system misbehaves in ways that seem physically impossible — a 115200 baud line delivering 62 KB/s — suspect the instrument before the system.

Reclaim order, safest first

  1. Uploaded images in the archive — the server already holds them
  2. Rotated logs and old database backups — oversized live logs are truncated, not deleted, so services holding the file descriptor keep writing
  3. Synced sensor_readings rows, oldest first
  4. Oldest un-uploaded images — last resort only

Invariant: un-uploaded sensor data is never deleted. Row deletion is bounded below by the lowest sensor_readings.id still queued for upload, with a hard floor of 10,000 rows retained regardless. If the space floor cannot be reached without touching un-uploaded sensor data, the guard stops and logs an error rather than trading data for disk.

Justifying stage 4 — the only stage that deletes unsent data

Letting the card fill stops SQLite writes, which stops acknowledgements, which overflows the node’s one-hour buffer and loses gas readings — the primary measurement — in order to preserve photographs. Shedding the oldest images is strictly the better outcome. It is configurable off, in which case the guard fails loudly instead.

VACUUM safety. VACUUM rebuilds the database into a temporary copy and briefly needs as much free space again as the file occupies. Running it while nearly full is how a low-disk condition becomes a corrupt database. The guard skips VACUUM below 1.2× the database size; deleted pages remain available for reuse, so writes continue either way.

The quality label distribution is 100 % EXCELLENT across all 3,172 readings. There is no class variation whatsoever.

This is a systems validation dataset. It demonstrates that the pipeline transports, timestamps, deduplicates, stores and uploads correctly. It is not a spoilage dataset: it contains no meat, no spoilage progression and no ground-truth labels. The old polling client is disabled and now refuses to start without an explicit override. Running it alongside the BLE receiver would store every reading twice under two different source_id values — once keyed ESP32-MeatMonitor:<seq> from BLE, once keyed by the server’s own id from the polling path — which the UNIQUE index cannot recognise as the same measurement.

Unattended display

A launcher installed to ~/.config/autostart/ opens both pages at login with no manual step, run by lxsession-xdg-autostart from the labwc Wayland session. It waits for each server to answer before opening the browser — a connection-error page after boot is worse than a few seconds’ delay. Two implementation notes worth recording:

  • Chromium exits immediately if it cannot find the compositor, so the script must export XDG_RUNTIME_DIR, WAYLAND_DISPLAY and DISPLAY — an autostart context can inherit a minimal environment.
  • A duplicate-launch guard using bare pgrep -f <profile-path> matches the shell running the script, because the path appears in its own command line. The guard must verify the matched process is actually Chromium by reading /proc/<pid>/comm. The same self-matching trap caught pkill several times during debugging — worth a footnote in any methods section describing shell-based process management.

Limitations and threats to validity

State these explicitly. Several are disqualifying for claims a reader might otherwise assume.

  1. No spoilage data. All labels EXCELLENT; no class variation, no meat, no ground truth. The dataset validates the system, not the science.
  2. MQ cross-sensitivity is unaddressed. The same elements compute multiple gas concentrations with different coefficient pairs. Per-gas claims are not defensible without a reference instrument.
  3. R₀ calibration is single-point and drifts. Established once in ambient air, per unit, with no humidity or temperature compensation — while RH spanned 53.9–79.5 % in this dataset alone.
  4. BME280 thermally coupled to the MQ heaters. 33.8–39.1 °C is enclosure temperature, not sample temperature.
  5. Threshold sets are inconsistent between firmware and gateway, and POOR is unreachable.
  6. Single node, single gateway, single site. No replication, no multi-device concurrency. BLE tested with one peripheral; CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1.
  7. Short observation window. Continuous operation measured in hours, not the 72 h target. The 72 h storage figures are calculated from measured unit costs, not observed.
  8. Residual BLE reconnection churn is not root-caused. Not a data-loss path, but an unexplained behaviour.
  9. Disk-full behaviour verified by code path, not by filling a disk.
  10. Power-cut recovery verified by configuration audit, not by an actual power cut.
  11. BLE findings are specific to this stack pairing. BlueZ 5.82 / bleak 3.0.2 / NimBLE 2.2.x. May not generalise to other centrals or to Bluedroid.
  12. Single-server dependency. One cloud host, no failover; “backed up” means one remote copy.

What is defensible, and what is not

Defensible from this work

Supported
  • An architecture in which the gateway, not the cloud, is the point of durability, with a stated and mechanised delivery guarantee.
  • A store-and-forward protocol over BLE GATT with cumulative acknowledgement, and the ordering argument that makes an acknowledgement mean “durably stored”.
  • Timestamp reconstruction on a node with no RTC and no NTP, with per-row provenance recorded — and the observation that the pushed-clock mechanism proved unnecessary.
  • Flash-wear-aware persistence: zero flash writes in steady state.
  • Measured storage economics showing a 189× asymmetry between image and sensor streams, and a budget-based isolation mechanism derived from it.
  • The BlueZ/NimBLE interoperability findings with the measurement table. In my judgement the most publishable single contribution here — directly useful to other practitioners and not documented elsewhere that I could find.
  • A catalogue of durability defects reachable only by adversarial reasoning about the failure envelope, not by testing.

Not defensible without further work

Unsupported
  • Any classification accuracy, sensitivity, specificity or ROC figure.
  • Any claim that the thresholds correctly separate fresh from spoiled meat.
  • Any claim about shelf-life prediction or correlation with microbial load.
  • Any per-gas quantitative accuracy claim.
  • Any claim of 72 h continuous validated operation — projected, not observed.
  • Any general claim about “BLE reliability” beyond this stack pairing.

Open questions

  1. Root-cause the ≈30 s reconnection churn. A btmon HCI capture correlated against the node’s serial log across a single disconnect would settle it.
  2. Test whether the write instability reproduces under Bluedroid, and with other centrals. This determines whether §01 is a NimBLE issue, a BlueZ issue, or an interaction — and it is the fastest way to raise the finding’s generality.
  3. Run the actual spoilage experiment. Controlled temperature, real samples, time course, independent ground truth. Everything scientific depends on this.
  4. Humidity and temperature compensation for MQ readings, plus periodic R₀ re-baselining.
  5. Thermally isolate the BME280 from the heater array.
  6. Reconcile the two threshold sets, and either implement or remove POOR.
  7. Verify power-cut recovery with a real power cut, and disk-full behaviour by actually filling a disk.
  8. Extend the node buffer. 1,200 readings is the current limit; 2,400 overflowed DRAM by 22,832 bytes. A more compact on-node record — scaled 16-bit integers instead of floats, ≈26 B versus 44 B — would roughly double capacity within the same RAM.
  9. Multi-node scaling. One peripheral, one connection today. Several nodes per gateway changes the BLE scheduling picture substantially.
  10. A second backup destination, so “backed up” is not one remote host.

A note on method, possibly worth a paragraph of its own

The largest single time cost in this project was not design or implementation. It was that the diagnostic channel itself was compromised, so early evidence actively misled. Hours went into pursuing a phantom “serial flood” and an “impossible data rate” that were artefacts of ModemManager interference and kernel TTY buffering.

The general lesson generalises well beyond this project: when a system misbehaves in ways that seem physically impossible, suspect the instrument before the system.
